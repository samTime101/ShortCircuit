# Portable IR — `shortcircuit.ir/v1`

The IR is the executable contract between the compiler and every consumer:
simulator, test runner, truth table, graph view, JSON panel, and future
backends. It is plain JSON, contains no source AST objects, and encodes every
value as a zero-padded binary string.

```ts
interface ProgramIR {
  schema: "shortcircuit.ir/v1";
  language: "logicflow/0.1";
  circuits: CircuitIR[];
  tests: TestSuiteIR[];
}
```

- One `CircuitIR` per `CIRCUIT` block, in source order.
- One `TestSuiteIR` per `TEST` block, in source order.
- `ir` is `null` whenever compilation has any error. Consumers must not treat a
  partial circuit list as executable.
- Warnings do not block the IR. Errors do.

A complete example appears at the end of this document.

---

## 1. Circuit

```ts
interface CircuitIR {
  name: string;
  line: number;
  inputs: CircuitInput[];
  outputs: CircuitOutput[];
  states: CircuitState[];
  nodes: CircuitNode[];
  events: ClockEvent[];
  sequential: boolean;
  stats: {
    nodes: number;
    states: number;
    events: number;
    maxDepth: number;
    maxWidth: number;
  };
}
```

| Field | Contract |
| --- | --- |
| `name` | Source circuit name, case-sensitive |
| `line` | 1-based declaration line |
| `inputs` | Ports, in declaration order; order defines positional binding |
| `outputs` | Exposed outputs, in declaration order |
| `states` | State elements reachable in this top-level circuit |
| `nodes` | Flat graph, including every instantiated child scope |
| `events` | Clocked blocks that update at least one state |
| `sequential` | `true` when `states.length > 0` or `events.length > 0` |
| `stats.nodes` | Number of nodes in `nodes` |
| `stats.states` | Number of state elements |
| `stats.events` | Number of clock events |
| `stats.maxDepth` | Longest combinational dependency chain, in nodes |
| `stats.maxWidth` | Widest node in the circuit, in bits |

Circuits are compiled independently. A top-level circuit contains the
flattened graph for all instances it uses; there are no links between
`CircuitIR` entries at runtime.

### 1.1 Inputs

```ts
interface CircuitInput {
  name: string;
  width: number;
  line: number;
  column: number;
}
```

Inputs are leaves supplied by the host. Every input has a width of at least 1.
Names are unique within the circuit.

### 1.2 Outputs

```ts
interface CircuitOutput {
  name: string;      // full path, e.g. "result.sum"
  portName: string;  // last segment, e.g. "sum"
  node: string;      // node ID supplying the value
  width: number;
  line: number;
  column: number;
}
```

`name` preserves a dotted source path. `portName` is the short name used for
instance access and for test expectations when unambiguous. Multiple outputs
may share a short name; in that case only the full `name` is unambiguous.
An output may point directly at an input node (pass-through).

### 1.3 States

```ts
interface CircuitState {
  name: string;      // scoped, e.g. "outer.register.stored"
  node: string;      // state node ID
  width: number;
  init: string;      // zero-padded binary initial value
  line: number;
  column: number;
}
```

States are indexed by `name` in snapshots. Nested instances receive dotted
names from their scope path. `init` is always exactly `width` characters
long.

### 1.4 Statistics

Statistics are informational. They must be consistent with the arrays, but a
consumer must not rely on them for semantics. `maxDepth` is graph depth (an
input has depth 0), not instantiation depth.

## 2. Nodes

```ts
type NodeKind = "input" | "constant" | "state" | "operation";

interface CircuitNode {
  id: string;
  kind: NodeKind;
  op?: string;                 // operation nodes only
  width: number;
  label: string;               // display label, usually the signal name
  scope: string[];             // [] at top level; ["first", "inner"] inside instances
  operands: string[];          // node IDs, in operation-specific order
  value?: string;              // constants and states: binary value
  inputName?: string;          // input nodes: top-level input name
  params?: Record<string, string | number | boolean>;
  line: number;
  column: number;
}
```

### 2.1 Identity

- `id` is a unique string within the compiled program. Treat it as opaque.
- IDs currently look like `Adder8/op:3` or `FullAdder/first/in:a`, but layouts
  and serial counters may change. Never derive semantics by parsing an ID.
- `label` is for humans. It is not guaranteed unique.
- `scope` is the instance path local to the top-level circuit. An empty array
  means the node was written directly in the top-level circuit. It is not a
  globally unique name by itself.
- `line` / `column` are 1-based source locations. Nodes generated by a nested
  instance point at the instantiation site or the child source declaration,
  depending on the node; they are diagnostics aids.

### 2.2 Input nodes

```json
{
  "id": "Adder8/in:a",
  "kind": "input",
  "width": 8,
  "label": "a",
  "scope": [],
  "operands": [],
  "inputName": "a",
  "line": 2,
  "column": 1
}
```

An input node reads the host-supplied value named `inputName`. It is a leaf
with no operands. Exactly one input node exists per **top-level**
`CircuitInput`. Child-instance ports do not get their own input nodes: during
flattening they are wired directly to the parent node that supplies the port
value.

### 2.3 Constant nodes

```json
{
  "id": "Adder8/const:2",
  "kind": "constant",
  "width": 8,
  "label": "0",
  "scope": [],
  "operands": [],
  "value": "00000000",
  "line": 5,
  "column": 11
}
```

Constants are materialized at their **coerced** width. A literal `0` used in
an 8-bit comparison becomes an 8-bit constant node; the graph shows the actual
width used. `value` is always exactly `width` bits.

### 2.4 State nodes

```json
{
  "id": "Register8/state:stored",
  "kind": "state",
  "width": 8,
  "label": "stored",
  "scope": [],
  "operands": [],
  "value": "00000000",
  "line": 6,
  "column": 1
}
```

The node's `value` is its **initial** value. At runtime the simulator owns the
current state value separately and exposes it in `SimulationSnapshot.states`.
State nodes are leaves during combinational evaluation.

### 2.5 Operation nodes

Operation nodes consume `operands` in a fixed order and produce one value of
`width` bits. `params` carries compile-time constants (slice bounds, arity,
common input width) that the operation needs in addition to its operand
values.

Operations are **not** required to be NAND primitives. They are the semantic
primitives of LogicFlow. Backends that target a smaller gate set must lower
them explicitly.

## 3. Operation contracts

Let `w = node.width`, `mask(w) = 2^w - 1`, and `uint(bits)` be the unsigned
integer represented by an operand's zero-padded binary string.

All results are normalized to `w` bits. All arithmetic is unsigned.

| `op` | Operands | `params` | Contract |
| --- | --- | --- | --- |
| `AND` | ≥ 2 | `arity` | Bitwise AND of all operands |
| `OR` | ≥ 2 | `arity` | Bitwise OR of all operands |
| `XOR` | ≥ 2 | `arity` | Bitwise XOR of all operands |
| `NAND` | ≥ 2 | `arity` | `NOT(AND(...))` at width w |
| `NOR` | ≥ 2 | `arity` | `NOT(OR(...))` at width w |
| `XNOR` | ≥ 2 | `arity` | `NOT(XOR(...))` at width w |
| `NOT` | 1 | `arity: 1` | `(~a) & mask(w)` |
| `BUFFER` | 1 | `arity: 1` | `a` |
| `ADD` | 2 | `inputWidth` | `(a + b) & mask(w)`; w = inputWidth |
| `SUBTRACT` | 2 | `inputWidth` | `(a - b) & mask(w)`; w = inputWidth |
| `MULTIPLY` | 2 | `inputWidth` | `a * b`; w = 2 × inputWidth, so the full product fits (the mask is a no-op) |
| `DIVIDE` | 2 | `inputWidth` | `(a / b) & mask(w)` unsigned floor; `b = 0` raises `R500` |
| `EQUAL` | 2 | `inputWidth` | `1` if `a == b`, else `0`; w = 1 |
| `LESS` | 2 | `inputWidth` | `1` if `a < b`, else `0`; w = 1 |
| `GREATER` | 2 | `inputWidth` | `1` if `a > b`, else `0`; w = 1 |
| `COMPARE` | 2 | `inputWidth` | `0` equal, `1` less, `2` greater; w = 2 |
| `MUX` | 3: `a`, `b`, `select` | `selectZero: "a"`, `selectOne: "b"` | `select == 0 ? a : b`; select is 1 bit |
| `CONCAT` | ≥ 1 | `parts` | Operands are joined **most-significant first**; result width is the sum of operand widths |
| `SLICE` | 1 | `hi`, `lo` | `(a >> lo) & mask(hi - lo + 1)`; inclusive bounds; w = hi − lo + 1 |
| `SHIFT_LEFT` | 2: `value`, `amount` | — | `(value << amount) & mask(w)`; amount ≥ w gives 0; w = value width |
| `SHIFT_RIGHT` | 2: `value`, `amount` | — | `value >> amount`; amount ≥ w gives 0; w = value width |
| `DECODER` | 1: `select` | `selectWidth` | One bit set at index `select`; w = 2^selectWidth |
| `ENCODER` | 1 | `inputWidth` | Index of highest set bit; 0 gives 0; w = max(1, ceil(log2(inputWidth))) |
| `ZEXT` | 1 | `sourceWidth` | The value, widened to w bits with zeroes; w must not be smaller than the source |
| `SEXT` | 1 | `sourceWidth` | The value, widened to w bits by repeating the top bit |
| `POPCOUNT` | 1 | `sourceWidth` | Number of set bits; w = max(1, ceil(log2(sourceWidth + 1))) |
| `REDUCE_AND` | 1 | `sourceWidth` | 1 when every source bit is 1 |
| `REDUCE_OR` | 1 | `sourceWidth` | 1 when any source bit is 1 |
| `REDUCE_XOR` | 1 | `sourceWidth` | Parity of the source bits |
| `REPEAT` | 1 | `count`, `sourceWidth` | The value repeated `count` times; w = count x source width |
| `REVERSE` | 1 | `sourceWidth` | The value with its bit order reversed; w = source width |

Notes:

- `MUX` is defined for any 1-bit select. In well-formed IR only 0 or 1
  occurs, and any value other than 0 selects `b` in the reference
  implementation.
- `CONCAT` operand **widths** are read from the operand nodes, not from
  `params`. `params.parts` is only a count for inspection.
- `SLICE` uses constant bounds from `params`; its operand can be any width.
- Shift amounts are read as unsigned integers. Amounts wider than 32 bits are
  rejected at compile time, but the IR schema itself does not impose a width
  beyond the global limit.
- `DECODER` and `ENCODER` are included as operations because source-level
  `DECODER`/`ENCODER` calls are primitive language operations. A backend may
  lower them to shifts and priority logic.
- Unknown `op` values must be rejected (`R406` in the reference simulator),
  never guessed.

### 3.1 Topological order

`nodes` may be emitted in any order. A consumer must perform its own ordering
using `operands`; the reference simulator uses DFS post-order and rejects
cycles (`R407`) and missing IDs (`R408`).

All operand IDs must exist in the same `CircuitIR.nodes` array. There are no
cross-circuit node references.

## 4. Clock events

```ts
type ClockEdge = "rising" | "falling";

interface ClockEvent {
  id: string;
  edge: ClockEdge;
  clock: string;       // node ID
  scope: string[];
  updates: Array<{
    state: string;     // state node ID
    value: string;     // combinational node ID evaluated against old state
  }>;
  line: number;
  column: number;
}
```

Contract:

1. `clock` references a node of width 1.
2. On each input transition, evaluate the whole graph against the new inputs
   and the **old** state.
3. Compare the clock node's previous and current value:
   - rising fires on `0 → 1`;
   - falling fires on `1 → 0`.
4. For every fired event, read `value` from the graph just evaluated. That
   value was computed from pre-edge state.
5. Apply all `updates` from all fired events simultaneously. A conflict — two
   different values for one state in the same transition — is an error
   (`R405`).
6. Re-evaluate the graph with the committed state.

`scope` records the instance path of the block, for display. `updates` may be
in any order; simultaneous commit means order does not affect the result.
A state not listed in `updates` holds its value.

The compiler emits one event per `ON` block that updates at least one state.
A block that updates nothing is omitted (with warning W302). Two events that
drive the same state on the same edge and clock are rejected before IR is
produced (E312).

The state's initial value comes from `CircuitState.init` (also mirrored on the
state node's `value`). A new simulator starts with every state at its initial
value and captures clock values as the baseline; the first input transition is
what can fire events.

## 5. Test suites

```ts
interface TestSuiteIR {
  name: string;
  circuit: string;
  line: number;
  cases: TestCaseIR[];
  runnable: boolean;
  reason?: string;
}

interface TestCaseIR {
  label: string;
  line: number;
  /** Flat view of every input used in the case. */
  inputs: TestInputIR[];
  /** Flat view of every expectation in the case. */
  expectations: TestExpectationIR[];
  /** Ordered program, including STEP and CYCLE blocks. */
  program: TestInstructionIR[];
}

interface TestInputIR {
  name: string;
  width: number;
  value: string;    // zero-padded binary
  line: number;
  column: number;
}

interface TestExpectationIR extends TestInputIR {
  actualName: string;
}

type TestInstructionIR =
  | TestInputInstruction
  | TestExpectInstruction
  | TestLoadInstruction
  | TestStepInstruction
  | TestCycleInstruction;

interface TestInputInstruction {
  kind: "input";
  name: string;
  width: number;
  value: string;
  line: number;
  column: number;
}

interface TestExpectInstruction {
  kind: "expect";
  name: string;
  actualName: string;
  target: "output" | "state";
  width: number;
  value: string;
  line: number;
  column: number;
}

interface TestLoadInstruction {
  kind: "load";
  name: string;
  width: number;
  value: string;
  line: number;
  column: number;
}

interface TestStepInstruction {
  kind: "step";
  statements: TestInstructionIR[];
  line: number;
  column: number;
}

interface TestCycleInstruction {
  kind: "cycle";
  clock: string;
  count: number;
  line: number;
  column: number;
}
```

### 5.1 Suite

- `name` and `circuit` are both the target circuit name in v1.
- `runnable` is true for every suite that compiled. Clocked suites run like
  combinational ones; the field remains so a host can report a suite it
  cannot execute.
- `cases` preserve source order.

### 5.2 Case inputs

Each `TestInputIR` has:

- `name`: the circuit input name, used by the simulator;
- `width`: the input width at compile time;
- `value`: exactly `width` binary characters;
- source location.

The flat `inputs` list is a convenience view. A combinational case sets
every circuit input exactly once; a sequential case may set an input more than
once, and an input that is never set keeps its last value, starting at zero.

### 5.3 Expectations

`TestExpectationIR` is an input-shaped record plus `actualName`:

- `name`: port name used for display and short lookups (often the same as
  `actualName`);
- `actualName`: full output name used to index `SimulationSnapshot.outputs`;
- `width`, `value`: expected binary value;
- source location.

Consumers must compare the **entire** binary string, including leading zeros.
A case passes when every expectation matches. If simulation throws, the case
fails and records the error; no expectation is reported as passing.

### 5.4 The program

`program` is the ordered instruction list. It is the authoritative form; the
flat `inputs` and `expectations` lists are views of it.

| Instruction | Meaning |
| --- | --- |
| `input` | Apply one input value. One transition. |
| `expect` | Compare an output or state with the current value. `target` says which. |
| `load` | Force a state to a value, without firing a clock edge. |
| `step` | Apply every `input` inside it as one transition, then check its `expect` instructions. |
| `cycle` | Pulse a clock 0 → 1 → 0 `count` times. Each pulse is one transition. |

A step counter advances for every input, load, step, and cycle. It is what a
failure message reports.

### 5.5 Executing suites

A portable runner can:

1. find the target `CircuitIR` by `suite.circuit`;
2. for each case, create a fresh simulator (state initialized from IR);
3. walk `case.program` in order, applying inputs, loads, steps, and cycles;
4. compare expected values at the point each expectation is reached;
5. stop the case at the first failure and report the step;
6. aggregate pass/fail counts.

The test runner itself is not part of the IR. `runnable`, the program, and
the flat views are.

## 6. Values

### 6.1 Binary strings

Every serialized value — node constants, state initializers, test values,
snapshots, truth-table cells — is a string of `0` and `1`:

- most-significant bit first;
- exactly `width` characters;
- no `0b` prefix, spaces, underscores, or decimal notation;
- the empty string is never valid for a value (but a truth-table cell may be
  empty if an output is missing, which indicates invalid IR/host behavior).

```text
width 1: "0" or "1"
width 4: "0000" … "1111"
width 8: "00000000" … "11111111"
```

### 6.2 Integers

All values are unsigned integers in `[0, 2^width - 1]`. There is no sign bit,
no two's-complement interpretation, and no floating point. `decimal` fields in
snapshots are exact base-10 strings produced from arbitrary-precision
integers; they are a convenience for display only.

### 6.3 Widths

Every node and port has an integer width from 1 to the compile-time
`maxWidth` (default 4096). The IR does not carry the limit; a consumer should
enforce its own safe bound when loading untrusted IR.

### 6.4 No unknown values

The schema is two-state. `X`, `Z`, high-impedance, and don't-care values are
not representable. A backend that needs four-state simulation must extend the
schema and bump the version.

## 7. Serialization and stability

- JSON property order is not significant.
- Unknown extra properties should be ignored by consumers for forward
  compatibility within v1; unknown required semantics (new node ops) must not
  be guessed.
- Node IDs, labels, stats, line/column, and test labels are informational.
  Operation semantics are normative.
- The schema string changes only for a breaking shape change. Additive fields
  within v1 are allowed; consumers should tolerate them.
- `language` identifies the source language version. A consumer that executes
  IR does not need to parse source, but it may want to display the version.
- Source text is not embedded. Diagnostics are not part of the IR; they belong
  to the compile result.

### Version compatibility checklist

| Check | Action if unsupported |
| --- | --- |
| `schema === "shortcircuit.ir/v1"` | Reject or migrate |
| `language` starts with `logicflow/` | Warn, attempt if version known |
| Node width in `[1, localMaxWidth]` | Reject |
| Every operand ID exists | Reject |
| Node graph is acyclic | Reject |
| Every `op` is known | Reject |
| Every event clock is 1 bit | Reject |
| Every update target is a state node | Reject |
| Every update value node exists | Reject |

## 8. Full JSON example

Source:

```logicflow
CIRCUIT Adder8
  INPUT a : BUS(8)
  INPUT b : BUS(8)

  sum = ADD(a, b)
  is_zero = EQUAL(sum, 0)

  OUTPUT sum
  OUTPUT is_zero
END

TEST Adder8
  CASE "1 + 2"
    INPUT a = 00000001
    INPUT b = 00000010
    EXPECT sum = 00000011
    EXPECT is_zero = 0
  END
END
```

operand, so the analyzer creates `Adder8/const:2` at width 8. The original
one-bit constant remains in `nodes` as an unconsumed leaf; the compiler does
not prune coercion artifacts. Consumers must follow `operands` from outputs
rather than assuming every node is live. Widths are explicit throughout.

## 9. Porting checklist

A minimal independent runtime should:

1. **Parse and validate JSON** against the schema and language version.
2. **Validate widths and IDs** before allocating memory proportional to widths.
3. **Build the node map** and reject duplicate IDs.
4. **Topologically order** the graph; reject cycles and missing operands.
5. **Implement every operation** with exact unsigned semantics and masking.
   Wrap arithmetic only as specified; raise on divide-by-zero.
6. **Initialize state** from `CircuitState.init` and capture clock baselines.
7. **Apply transitions**: evaluate, detect 0→1 / 1→0 clock edges, evaluate
   update expressions against old state, commit simultaneously, detect
   conflicting writes, re-evaluate.
8. **Expose snapshots** keyed by input/output/state names with exact binary
   and decimal values.
9. **Run test suites** by constructing a fresh simulator per case and comparing
   whole binary strings.
10. **Enumerate truth tables** only when `sequential === false`, with an
    explicit cap and reason instead of partial results.
11. **Treat `ir: null`** (from compilation) as non-executable.
12. **Preserve clock event semantics** when targeting hardware or another
    language; simultaneous commit is not an implementation detail.

The reference implementation lives in `packages/engine/src`; its behavior is
the conformance test for this document.
